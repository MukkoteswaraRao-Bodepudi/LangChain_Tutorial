1. WHAT IS LANGSMITH?
============================================================

LangSmith is a platform from the LangChain ecosystem for developing,
debugging, evaluating, testing, and monitoring applications powered by
large language models (LLMs).

LLM applications are different from traditional applications because
their behavior is often probabilistic.

A traditional application might behave like:

Input
  |
  v
Function
  |
  v
Database
  |
  v
Output

An LLM application can look like:

User
 |
 v
Query Transformation
 |
 v
Retriever
 |
 v
Vector Database
 |
 v
Prompt Construction
 |
 v
LLM
 |
 v
Tool
 |
 v
LLM
 |
 v
Output Parser
 |
 v
Final Answer

When the final answer is wrong, simply looking at the answer does not
tell us where the problem occurred.

LangSmith provides visibility into the execution.

A useful mental model is:

LangChain / LangGraph
        |
        v
Build the application
        |
        v
LangSmith
        |
        +--> Trace
        +--> Debug
        +--> Evaluate
        +--> Test
        +--> Monitor
        +--> Improve

In simple terms:

LangChain = build LLM applications
LangGraph = build stateful agent workflows
LangSmith = observe and evaluate those applications


============================================================
2. WHY LLM APPLICATIONS NEED OBSERVABILITY
============================================================

Observability means understanding what happened inside a system by
examining its recorded execution data.

Traditional applications normally use:

- Logs
- Metrics
- Traces
- Error reports

LLM applications require additional information:

- Prompts
- Model inputs
- Model outputs
- Retrieved context
- Tool calls
- Tool outputs
- Agent decisions/actions
- Token usage
- Latency
- Evaluation scores
- User feedback

Consider a RAG system.

User asks:

"What is a Kubernetes Deployment?"

The application returns an incorrect answer.

Possible causes:

1. Query transformation failed.
2. Embedding was poor.
3. Retriever selected incorrect documents.
4. Chunking was poor.
5. Reranker selected the wrong chunks.
6. Prompt was poorly constructed.
7. LLM misunderstood the context.
8. Output parser failed.

Without observability, developers may incorrectly change the LLM
prompt even though the actual problem is retrieval.

With LangSmith, the complete execution can be inspected.

This leads to an important production principle:

Do not debug only the final answer.
Debug the complete execution path.

TRACE

A trace represents the execution of an application request.

Example:

Trace ID: abc123

User Request
     |
     +-- Retrieval
     |
     +-- Prompt
     |
     +-- LLM
     |
     +-- Parser
     |
     +-- Final Answer


RUN

A run represents an individual operation inside the trace.

For example:

Run 1 = Retriever
Run 2 = Prompt
Run 3 = LLM
Run 4 = Parser

A trace can contain many runs.


DATASET

A dataset is a collection of test examples.

Example:

Question:
"What is a Kubernetes Deployment?"

Expected answer:
"A Deployment manages a set of replicated Pods."

A dataset may contain hundreds or thousands of examples.


EVALUATOR

An evaluator determines how good an output is.

Examples:

- Correctness
- Relevance
- Faithfulness
- Toxicity
- Retrieval quality


EXPERIMENT

An experiment runs an application against a dataset and evaluates
the results.

This allows comparison between:

Prompt A vs Prompt B
Model A vs Model B
Retriever A vs Retriever B


FEEDBACK

Feedback is a signal associated with a run.

Examples:

- User thumbs up
- User thumbs down
- Rating
- Human evaluation
- Automated evaluator score

4. TRACING: THE MOST IMPORTANT CONCEPT
============================================================

Tracing is one of the most important LangSmith capabilities.

Imagine a user asks:

"Explain Kubernetes Services."

A RAG application may execute:

1. Receive question
2. Generate embedding
3. Search vector database
4. Retrieve chunks
5. Build prompt
6. Call LLM
7. Parse answer
8. Return answer

A trace records these steps.

Conceptually:

Trace
 |
 +-- Query
 |
 +-- Retriever
 |     |
 |     +-- Embedding
 |     +-- Vector Search
 |     +-- Retrieved Documents
 |
 +-- Prompt
 |
 +-- LLM
 |
 +-- Output Parser
 |
 +-- Final Answer

This is called an execution tree.

Tracing answers:

"What exactly happened when this request was processed?"

Useful information includes:

- Input
- Output
- Execution time
- Model
- Prompt
- Token usage
- Errors
- Metadata
- Intermediate results
- Tool calls
- Retrieved documents

9. DEBUGGING RAG WITH TRACES
============================================================

Consider:

Question:
"What is a Kubernetes Deployment?"

Ground-truth relevant chunks:

[20, 406, 481]

Retrieved chunks:

[4, 20, 259, 406, 1]

Only chunks 20 and 406 are relevant.

Possible issue:

Retriever did not retrieve chunk 481.

The final answer may therefore be incomplete.

LangSmith allows us to inspect:

Query
  |
  v
Retriever
  |
  +--> chunk 4
  +--> chunk 20
  +--> chunk 259
  +--> chunk 406
  +--> chunk 1
  |
  v
Prompt
  |
  v
LLM
  |
  v
Answer

Now the developer knows the issue occurred before generation.

This distinction is extremely important:

Retrieval failure != Generation failure.

If the retriever provides bad context and the LLM produces an answer
based on that context, changing the LLM may not solve the problem.


RAG FAILURE CATEGORIES

A. Retrieval failure

Correct information exists but is not retrieved.

Possible solutions:

- Better chunking
- Better embeddings
- Hybrid search
- Reranking
- Query rewriting
- Metadata filters
- Better retrieval parameters


B. Context failure

Relevant documents are retrieved but the context sent to the model
is incomplete or poorly organized.

Possible solutions:

- Better context selection
- Context compression
- Reranking
- Better prompt construction


C. Generation failure

The correct context is provided but the model generates an incorrect
answer.

Possible solutions:

- Prompt improvement
- Better model
- Structured output
- Additional validation
- Grounding instructions

Without a dataset:

Developer changes prompt
       |
       v

       |
       v
Looks good
       |
       v
Deploys

Problem:

With a dataset:

Developer changes prompt
       |
       v

       |
       v
Evaluate
       |
       v

       |
       v

This is much closer to software engineering practices.

11. EVALUATION FUNDAMENTALS
============================================================

Evaluation asks:

"How good is my LLM application?"

Possible dimensions:

1. Correctness
2. Relevance
3. Faithfulness
4. Completeness
5. Retrieval quality
6. Safety
7. Latency
8. Cost

Evaluation can be:

- Rule-based
- Exact match
- Human evaluation
- LLM-as-a-Judge
- Statistical metrics
- Retrieval metrics

For example:

Question:
"What is RAG?"

Expected:
"RAG retrieves relevant external information and provides it to an
LLM to improve the generated answer."

Generated:
"RAG retrieves information from an external knowledge source and gives
it to the LLM."

This may be considered correct even though it is not textually identical.

Therefore exact string matching is often insufficient for generative
applications.


============================================================
12. RAG EVALUATION METRICS
============================================================

RAG should generally be evaluated in two stages:

1. Retrieval evaluation
2. Generation evaluation


RETRIEVAL METRICS

PRECISION

Precision asks:

"Of the documents I retrieved, how many were relevant?"

Formula:

Precision = Relevant Retrieved Documents / Total Retrieved Documents

Example:

Retrieved = 5
Relevant = 2

Precision = 2 / 5 = 0.4


RECALL

Recall asks:

"Of all relevant documents, how many did I retrieve?"

Formula:

Recall = Relevant Retrieved Documents / Total Relevant Documents

Example:

Relevant documents = 3
Retrieved relevant documents = 2

Recall = 2 / 3 = 0.667


MRR

Mean Reciprocal Rank evaluates how early the first relevant result
appears.

For one query:

If first relevant result is rank 1:

RR = 1

If first relevant result is rank 2:

RR = 1/2 = 0.5

If first relevant result is rank 5:

RR = 1/5 = 0.2

MRR is the average reciprocal rank across queries.


NDCG

Normalized Discounted Cumulative Gain evaluates ranking quality and
can handle graded relevance.

It is useful when:

Rank 1 document is highly relevant
Rank 2 document is moderately relevant
Rank 3 document is irrelevant

The ordering matters.


GENERATION METRICS

Common dimensions:

- Correctness
- Relevance
- Faithfulness
- Completeness

FAITHFULNESS

Faithfulness asks:

"Is the answer supported by the provided context?"

Example:

Context:
"Kubernetes Deployments manage ReplicaSets."

Answer:
"Deployments manage ReplicaSets."

Faithful.

If the answer says:
"Deployments automatically manage database backups."

That claim is unsupported by the context.


============================================================
13. LLM-AS-A-JUDGE
============================================================

An LLM can evaluate another LLM's output.

Example:

Question:
"What is RAG?"

Context:
"RAG retrieves relevant documents and provides them to an LLM."

Answer:
"RAG retrieves external information and gives it to an LLM."

Evaluator:

Correctness: 9/10
Faithfulness: 10/10
Relevance: 10/10

This is called LLM-as-a-Judge.

A judge prompt might conceptually ask:

Evaluate the generated answer using the following criteria:

1. Is it correct?
2. Is it supported by the context?
3. Is it relevant to the question?
4. Does it contain unsupported claims?

The evaluator can return a structured score.

Important limitations:

- Judge model can make mistakes.
- Judge can prefer verbose answers.
- Judge can have biases.
- Poor evaluation prompts produce poor scores.
- Reference answers may themselves be incomplete.

Best practice:

Use multiple evaluation methods when possible.

For example:

Human evaluation
+
Rule-based checks
+
LLM-as-a-Judge
+
Retrieval metrics


============================================================
14. EXPERIMENTS AND REGRESSION TESTING
============================================================

Experiments allow systematic comparison.

Suppose you change a prompt.

Old prompt:

"Answer the question."

New prompt:

"Answer only using the provided context. If the answer is not present,
say that you do not know."

Run both prompts against the same dataset.

Example:

                Old       New
Accuracy        82%       89%
Faithfulness    84%       94%
Relevance       90%       92%
Latency         1.2 sec   1.3 sec

The new prompt appears better.

This is more reliable than saying:

"The new prompt feels better."


REGRESSION TESTING

Regression means a change that improves one behavior may accidentally
break another.

Example:

Version 1:
Accuracy = 88%

Version 2:
Accuracy = 91%

Looks better.

But perhaps:

Category A:
95% -> 96%

Category B:
87% -> 90%

Category C:
82% -> 70%

Overall average increased, but Category C became much worse.

Therefore inspect evaluation results by category, not only one overall
score.

PROMPT COMPARISON

MODEL COMPARISON

Model A:
High quality, higher latency.

Model B:
Lower quality, lower latency.

Model C:
Balanced.

Production selection should consider:

Quality
+
Latency
+
Cost
+
Reliability
+
Context window
+
Tool calling capability

The best model is not always the most powerful model.

The best production model is the one that satisfies the application's
quality, latency, cost, and reliability requirements.

18. COST, LATENCY, AND RELIABILITY
============================================================

Production LLM systems must balance quality with operational cost.

Important metrics include:

LATENCY

How long does a request take?

Example:

Retriever = 100 ms
Reranker = 200 ms
LLM = 1800 ms
Parser = 50 ms

Total approximately:

2150 ms

If users complain that the system is slow, tracing shows where the
time is spent.

TOKEN USAGE

Track:

- Input tokens
- Output tokens
- Total tokens

High token usage may indicate:

- Excessive context
- Long prompts
- Repeated model calls
- Agent loops

COST

Cost depends on the model/provider and token usage.

If an agent calls an LLM five times for a single question, cost may
increase significantly.

Tracing helps identify repeated calls.

RELIABILITY

Monitor:

- Error rate
- Tool failures
- Timeout rate
- Retry count
- Agent loops
- Failed requests

19. PRACTICAL RAG DEBUGGING WORKFLOW
============================================================

Scenario:

A user reports:

"The RAG application is giving wrong answers."

STEP 1 — Inspect the trace

Check the complete execution.

STEP 2 — Check the query

Was the original question correctly interpreted?

STEP 3 — Check retrieval

Which chunks were returned?

STEP 4 — Check relevance

Are those chunks actually relevant?

STEP 5 — Check ranking

Are the best chunks near the top?

STEP 6 — Check context

What exact text was provided to the LLM?

STEP 7 — Check prompt

Was the instruction clear?

STEP 8 — Check model response

Did the model use the context correctly?

STEP 9 — Classify failure

Possible classification:

Retrieval failure
Context failure
Generation failure
Parsing failure

STEP 10 — Fix the relevant component

Do not automatically change the LLM.

STEP 11 — Add the failure to the dataset

This prevents the same failure from returning later.

STEP 12 — Run regression evaluation

Compare the new version against the previous version.

============================================================
22. COMMON MISTAKES
============================================================

MISTAKE 1:
Only looking at the final answer.

Why wrong:
The problem may be retrieval, tools, prompts, or parsing.

Better:
Inspect the complete trace.


MISTAKE 2:
Evaluating with only one question.

Why wrong:
One example is not representative.

Better:
Create a representative evaluation dataset.


MISTAKE 3:
Using only exact-match evaluation.

Why wrong:
Generative answers can be semantically correct without matching the
reference text.

Better:
Combine semantic, rule-based, and human/LLM evaluation.


MISTAKE 4:
Changing the model before debugging retrieval.

Why wrong:
A powerful model cannot reliably answer from missing context.

Better:
First inspect retrieval quality.


MISTAKE 5:
Ignoring production traffic.

Why wrong:
Real users create unexpected queries.

Better:
Monitor production traces and convert important failures into
evaluation cases.


MISTAKE 6:
Tracking only accuracy.

Why wrong:
A system can have good quality but unacceptable latency or cost.

Better:
Track quality + latency + cost + reliability.


MISTAKE 7:
Not doing regression testing.

Why wrong:
A prompt change can improve one case and break another.

Better:
Run the evaluation dataset after important changes.

============================================================
24. INTERVIEW QUESTIONS AND ANSWERS
============================================================

Q1. What is LangSmith?

Answer:

LangSmith is an observability and evaluation platform for LLM
applications. It provides tracing, debugging, datasets, evaluation,
experimentation, feedback, and monitoring capabilities. It is
particularly useful for LangChain, LangGraph, RAG, and agent-based
applications.


Q2. Why is LangSmith useful for RAG?

Answer:

LangSmith allows developers to inspect the complete RAG execution,
including the user query, retrieval results, context passed to the
LLM, prompt, model output, and latency. This helps distinguish
retrieval failures from generation failures.


Q3. What is tracing?

Answer:

Tracing records the execution path of an application. A trace can
contain multiple runs representing operations such as retrieval,
prompt construction, model calls, tool execution, and output parsing.


Q4. What is a dataset?

Answer:

A dataset is a collection of test examples used to evaluate an LLM
application. It can contain inputs, reference outputs, metadata, and
other information required for testing.


Q5. What is an experiment?

Answer:

An experiment evaluates a particular version of an application against
a dataset. Experiments allow developers to compare prompts, models,
retrievers, or application versions.


Q6. What is LLM-as-a-Judge?

Answer:

LLM-as-a-Judge uses an LLM as an evaluator to score generated outputs
according to criteria such as correctness, relevance, and
faithfulness.


Q7. How do you debug a RAG system using LangSmith?

Answer:

I inspect the trace from the original query through query
transformation, retrieval, reranking, context construction, prompt
generation, LLM invocation, and final response. I determine whether
the failure occurred during retrieval, context construction,
generation, or parsing and then fix the relevant component.


Q8. What metrics would you use for RAG retrieval?

Answer:

Common retrieval metrics include Precision@K, Recall@K, MRR, and
NDCG. Precision measures the proportion of retrieved results that are
relevant, while recall measures how many of the relevant results were
retrieved.


Q9. How do you evaluate generation quality?

Answer:

I would evaluate correctness, relevance, faithfulness, and
completeness. Depending on the application, I would combine
rule-based evaluation, reference-based evaluation, LLM-as-a-Judge,
and human evaluation.


Q10. Why is regression testing important?

Answer:

LLM applications can change behavior when prompts, models, retrieval
settings, or code change. Regression testing ensures that improvements
do not accidentally degrade existing use cases.


Q11. How does LangSmith help with agents?

Answer:

It traces agent execution, including model calls, tool selection,
tool inputs and outputs, iterations, errors, and final responses. This
helps developers understand why an agent selected a particular path.


Q12. Is LangSmith an LLM?

Answer:

No. LangSmith is an observability, evaluation, testing, and monitoring
platform for LLM applications. It does not replace the LLM.


Q13. Is LangSmith the same as LangChain?

Answer:

No.

26. FINAL CHEAT SHEET
============================================================

LANGSMITH

Purpose:
Observability + Evaluation + Testing + Monitoring for LLM applications.

TRACE:
Shows what happened.

RUN:
Individual operation inside a trace.

DATASET:
Collection of evaluation/test examples.

EVALUATOR:
Scores application output.

EXPERIMENT:
Runs an application against a dataset and compares results.

FEEDBACK:
Human or automated signal about a run.

OBSERVABILITY:
Understand system behavior.

RAG:
Trace query -> retrieval -> context -> prompt -> LLM -> answer.

AGENT:
Trace model -> tool selection -> tool -> result -> next action.

RETRIEVAL METRICS:
Precision
Recall
MRR
NDCG

GENERATION METRICS:
Correctness
Relevance
Faithfulness
Completeness

PRODUCTION METRICS:
Latency
Token usage
Cost
Error rate
Retry rate
User feedback

MOST IMPORTANT DEBUGGING PRINCIPLE:

Wrong answer
    |
    +--> Retrieval problem?
    |
    +--> Context problem?
    |
    +--> Prompt problem?
    |
    +--> Model problem?
    |
    +--> Tool problem?
    |
    +--> Parsing problem?

Do not assume the LLM is the problem.
